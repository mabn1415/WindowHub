# WindowHub（仮称）— アプリケーション設計・実装引き継ぎ仕様書

## 0. 本文書の目的

これまでの設計検討を引き継ぎ、macOSとWindowsの両方で使用できるウィンドウ配置・管理アプリケーションを実装する。

現時点でのプロジェクト名は **WindowHub（仮称）** とする。正式名称とアプリアイコンは後から変更できる構造にする。

本プロジェクトでは、まず設計内容を正確に把握した上で、実際に起動・動作確認できるアプリケーションを作成することを目標とする。

既に作成されたプロトタイプやプロジェクトが存在する場合は、その内容を確認し、既存の成果物を活用すること。既存のファイルやコードを不用意に上書き・削除しない。

---

# 1. アプリケーションの基本コンセプト

## 1.1 開発目的

macOSとWindowsで共通した操作体系を持つ、キーボード中心のウィンドウ配置・管理アプリケーションを開発する。

既存のRectangleやPowerToys FancyZonesのようなウィンドウ配置機能を参考にしつつ、以下の特徴を持たせる。

1. キーボードのみで基本操作から高度な配置編集まで完結できる。
2. macOSとWindowsで同じハブUI・ショートカット体系を使用できる。
3. 複数モニターを1つの作業環境として管理できる。
4. 1モニターに複数のアプリ・ウィンドウを自由な比率で配置できる。
5. 分割配置だけでなく、同じ領域に複数ウィンドウを重ねられる。
6. モニター構成ごとに初期レイアウトを作成・保存できる。
7. 過去の配置履歴から、ユーザーの配置習慣を学習・提案できる。
8. アースカラーを基調とした、知的で近未来的な独自UIを採用する。
9. テーマやショートカットをユーザー自身がカスタマイズできる。

単なる画面分割ソフトではなく、**ユーザーの作業環境を記憶し、複数モニターにまたがるウィンドウの配置を効率化するツール**として設計する。

## 1.2 アプリの設計思想

以下の原則を重視する。

- Keyboard Driven：基本的にすべての機能をキーボードで操作可能にする。
- Minimal Interaction：操作回数を最小限にする。
- Predictable Behavior：ユーザーの意図しないウィンドウ移動を避ける。
- Adaptive Layout：モニター構成や利用履歴に応じた配置候補を提示する。
- Cross-platform Consistency：OSによって見た目や基本操作が変わらないようにする。
- Progressive Disclosure：単純な操作では最小限のUIを表示し、複雑な操作時のみ詳細画面を展開する。

見た目の演出を優先するのではなく、**使いやすさ・操作速度・情報の分かりやすさを第一に設計する**。

# 2. 対応OSと開発技術

## 2.1 対応OS

- macOS
- Windows 11を主対象とし、対応可能なWindows環境

両OSで同じアプリケーションの機能と操作体系を提供する。

ただし、OS固有のAPIや権限による制限は許容し、制限がある場合にはユーザーに分かる形で通知する。

## 2.2 推奨技術スタック

| 領域 | 技術 |
|---|---|
| デスクトップ基盤 | Tauri 2 |
| フロントエンド | React |
| UIロジック | TypeScript |
| バックエンド | Rust |
| macOSウィンドウ操作 | Accessibility API / AppKit / Core Graphics |
| Windowsウィンドウ操作 | Win32 API |
| 設定保存 | JSON |
| 配置履歴保存 | SQLiteなどのローカルDBを検討 |
| ショートカット | TauriプラグインおよびOS固有API |

レイアウトの計算、履歴管理、学習機能、UI、キーボード操作の状態管理は可能な限り共通化する。

ウィンドウ取得・移動・リサイズ・モニター検出などのOS依存処理は、共通インターフェースの背後に分離する。

## 2.3 クロスプラットフォーム設計

共通のWindowManagerインターフェースを設け、以下の操作を抽象化する。

- listWindows()
- getActiveWindow()
- listMonitors()
- moveWindow()
- resizeWindow()
- maximizeWindow()
- requestFullscreen()
- getMonitorConfiguration()
- observeWindowChanges()
- observeMonitorChanges()

上記は概念的なAPIであり、実際の名前やシグネチャは実装時に適切に設計してよい。

macOSとWindowsでできる限り同じ結果を得られるようにするが、すべてのアプリに対して同一動作を保証できない点を考慮する。

# 3. ウィンドウ配置機能

## 3.1 複数モニター対応

1台から複数台のモニターに対応する。

モニターごとに以下の設定を保持できるようにする。

- 分割数
- 分割方向
- 分割比率
- 領域数
- 配置するウィンドウ
- 重ねて配置するウィンドウ
- 最大化・全画面表示の設定
- レイアウトの固定状態

**1モニターにつき1アプリという前提にはしない。**

1つのモニターに2個、3個、5個以上のウィンドウを配置できる設計とする。

また、モニターごとに分割構造を変えられるようにする。

例えば、次のような配置を実現する。

### モニターA（縦置き）

- 上部55%：ブラウザ
- 下部45%：メモアプリとチャットアプリを重ねる

### モニターB（メイン）

- 左70%：エディタ
- 右30%：ターミナル

### モニターC（上段）

- 左60%：PDFビューア
- 右40%：ファイルマネージャー

これらを1回の操作で一括配置できるようにする。

## 3.2 配置方式

以下の3種類の配置をサポートする。

### Tile（分割配置）

複数のウィンドウを重ならないように配置する。

- 左右分割
- 上下分割
- 3分割
- 4分割
- 不均等分割
- カスタム分割

### Stack（重ねる配置）

複数のウィンドウを同一の領域・サイズに配置する。

例えば、右側40%の領域にChromeとFinderを重ねる。

アプリを前面に出す操作はOSや既存ランチャーに任せるため、独自のアプリ切り替え機能は原則として実装しない。

### Hybrid（分割＋重ねる配置）

TileとStackを組み合わせる。

**本アプリではHybrid方式を中心的な配置方式とする。**

すべてのウィンドウを細かく分割して画面内に押し込むのではなく、主要なウィンドウを大きく表示し、補助ウィンドウを別領域に配置・重ね合わせできるようにする。

# 4. 分割比率の設定

## 4.1 自由な比率設定

各モニターの分割比率はユーザーが変更可能とする。

例えば以下を設定できる。

- 50:50
- 60:40
- 70:30
- 75:25
- 任意のカスタム比率

2分割だけでなく、3分割以上の場合も各境界線を独立して調整できるようにする。

## 4.2 キーボード操作

ハブのEdit画面で比率を調整する。

基本操作案は以下の通り。

| キー | 操作 |
|---|---|
| `R` | 比率調整モードに入る |
| `[` / `]` | 編集する分割線を切り替える |
| 矢印キー | 5%単位で比率調整 |
| Shift + 矢印キー | 1%単位で微調整 |
| `0` | 選択した分割線を等分位置に戻す |
| Enter | 編集を確定 |
| Esc | 編集モードを終了・前画面へ戻る |

左右分割では左右方向、上下分割では上下方向のキーを利用する。

## 4.3 カーソル操作

キーボード中心の設計を維持しつつ、カーソルによる調整にも対応する。

- 分割線のドラッグ
- 比率スライダー
- 数値の直接入力

キーボードとカーソルのどちらで変更しても、同じレイアウトデータへ反映する。

ウィンドウ自体のリサイズ操作についても、取得可能な範囲で履歴学習の対象とする。

## 4.4 分割比率の保存

ユーザーが明示的に固定した比率は、学習結果によって勝手に上書きしない。

一時的な比率変更と、初期レイアウトとして保存する変更を区別する。

# 5. モニター構成別の初期レイアウト

## 5.1 採用する方式

**モニター構成ごとに、ユーザーが初回に手動設定したレイアウトを保存し、次回以降に再利用する方式を採用する。**

これは確定事項である。

初めて検出したモニター構成では、ユーザーが初期レイアウトを設定する。

既知の構成では、保存済みの初期レイアウトを読み込めるようにする。

PC起動やモニター接続のたびに、同じレイアウトをゼロから設定し直す必要はない。

## 5.2 モニター構成の識別

モニター番号のみを識別子にしない。

可能な範囲で次の情報を利用する。

- モニターの台数
- モニターの識別情報
- 解像度
- 縦横の向き
- 相対的な配置位置
- メインモニターの情報
- OSから取得できる接続情報

例えば、同じ3モニターでも、左右の配置を変更した場合や縦横の向きを変更した場合には、異なる構成として扱うか、類似する構成として照合できるようにする。

モニター識別情報が不安定な環境では、構成の特徴量を組み合わせたフォールバック判定を設ける。

## 5.3 初期レイアウトの適用

次の動作を基本とする。

1. 現在のモニター構成を検出する。
2. 保存済みの構成と照合する。
3. 一致する初期レイアウトがあれば読み込む。
4. ハブに配置プレビューを表示する。
5. ユーザーがEnterを押すと適用する。

**原則として、レイアウトの読み込みと実際のウィンドウ移動は別操作とする。**

モニター接続の変化だけで、作業中のウィンドウが勝手に動くことは避ける。

将来的に自動適用を許可する設定を追加することは可能だが、初期設定では手動確定を優先する。

## 5.4 レイアウト変更

保存済みレイアウトを変更した場合は、以下の2通りを選べるようにする。

- 今回だけ変更して適用
- 初期レイアウトを更新して保存

これにより、一時的な作業と普段の作業環境を区別する。

# 6. 配置履歴と学習機能

## 6.1 学習機能の目的

ユーザーが普段どのようにウィンドウを配置しているかを記録し、将来の配置候補に反映する。

学習対象は単純なアプリの座標だけではない。

**モニター構成・アプリの組み合わせ・分割比率・配置頻度・手動修正履歴**を考慮する。

## 6.2 記録する情報

- モニター構成
- アプリ識別子
- ウィンドウの識別情報
- 配置先モニター
- 配置領域
- ウィンドウの相対座標・サイズ
- 分割比率
- 同じ領域に配置されるアプリの組み合わせ
- 配置時刻
- 配置を変更した履歴
- 利用頻度・最近の傾向

画面内容や個人的な入力内容を収集する必要はない。

履歴は原則としてローカル保存とする。

ウィンドウタイトルは選択UIでは表示できてもよいが、プライバシーを考慮し、長期履歴への保存は必要性を検討する。

## 6.3 学習ルール

当初は大規模なAIモデルやクラウドAI APIを使用しない。

以下のようなルールベースの学習方式を基本とする。

1. 同じモニター構成での配置頻度を記録する。
2. 最近の配置に重みを付ける。
3. 繰り返し使用されるアプリの組み合わせを優先する。
4. 自動配置後にユーザーが手動修正した場合、その修正を重要な情報として扱う。
5. 一時的な移動や誤操作を過剰に学習しない。
6. ユーザーが固定した初期レイアウトを勝手に変更しない。

学習結果は「候補」として表示する。

## 6.4 配置の優先順位

以下の優先順位を採用する。

1. ユーザーが明示的に固定したレイアウト
2. 学習済みの配置候補
3. 履歴不足時の自動生成候補

ただし、新しいモニター構成の初期レイアウトを勝手に確定しない。

初期レイアウトはユーザーが設定する方針を維持し、学習結果や自動生成結果は作成を補助するものとする。

## 6.5 OS間の学習データ

macOSとWindowsでは、同じアプリでも識別子が異なる場合がある。

そのため、OS固有のアプリ識別子と共通アプリ識別子を対応付けられる設計が望ましい。

ただし、macOSとWindowsの間で学習履歴を自動同期する機能は初期実装の必須要件ではない。

設定のエクスポート・インポートは将来の拡張機能として検討する。

# 7. ハブUIのコンセプト

## 7.1 デザイン方針

ハブは次のコンセプトを採用する。

**Earth Tone × Minimal × Functional Futurism**

目指すのは、知的で落ち着いた、精密なプロフェッショナルツールのようなデザインである。

避けたい表現は以下の通り。

- AIチャットツールのような配色
- 青やシアンの強い発光
- 派手なネオン
- 強すぎるグラデーション
- ゲーミングUIのような装飾
- 過剰なガラス表現
- 不必要に大きな角丸
- 情報量の多すぎるダッシュボード

近未来感は配色や発光ではなく、**精密なレイアウト・余白・文字組み・滑らかな動作**で表現する。

## 7.2 Raycastとの関係

Raycastを参考にするのは、基本的に**ハブの表示位置と、呼び出したときに自然に現れる操作体験**である。

ハブそのものの外観や画面構造をRaycastに似せる必要はない。

特に、検索型ランチャーのコピーにはしない。

独自のウィンドウ配置専用ハブとして設計する。

## 7.3 ハブの表示位置

デフォルトでは、現在操作しているモニターの上部中央に表示する。

- 横方向は中央
- 縦方向はRaycastのように上寄り
- 作業領域や画面サイズに応じて調整
- マウスカーソル位置には依存しない
- モニターごとの配置情報を考慮

ハブは普段非表示とし、グローバルショートカットで表示する。

## 7.4 ハブの表示サイズ

概念的な初期サイズは以下の通り。

- Home：約540 × 300px
- Arrange：約720 × 460px
- Edit：約720 × 460px以上

具体的なサイズは、実際のUIの情報量と画面解像度に合わせて調整する。

普段は小さく、一括配置時や編集時に下方向へ自然に展開するUIを推奨する。

# 9. ハブの画面構成

ハブは主に以下の3画面で構成する。

1. Home
2. Arrange
3. Edit

Quick Move、保存済みワークスペース、Settingsについては、Homeからアクセスできる補助画面として実装する。

## 9.1 Home画面

ハブ起動直後に表示する画面。

表示する情報は以下を基本とする。

- アプリ名またはハブの識別表示
- 現在のモニター数
- 現在検出しているウィンドウ数
- 保存済み初期レイアウトの有無
- 主要機能
- キーボード操作ヒント

主要機能は以下とする。

| コマンド | 内容 |
|---|---|
| Arrange | 複数ウィンドウの一括配置 |
| Quick Move | 現在のウィンドウの移動 |
| Edit Layout | モニター内の分割構造・比率の編集 |
| Saved Workspaces | 保存済みレイアウトの管理・呼び出し |
| Settings | テーマ・ショートカットなどの設定 |

Home画面ではできるだけ情報を詰め込みすぎず、必要な操作へ素早く遷移できるようにする。

## 9.2 Arrange画面

複数ウィンドウを一括配置する画面。

**今回のアプリで最も重要な画面の1つである。**

以下の情報を表示する。

- 検出中のウィンドウ一覧
- 現在のモニター構成
- 各モニターの分割領域
- 各領域に割り当てられたウィンドウ
- 同じ領域に重ねられたウィンドウ数
- 配置予定のプレビュー
- 操作ヒント

基本的な画面構造は、左側にウィンドウ一覧、右側に全モニターの配置プレビューを設ける方式を推奨する。

利用するモニターが増えても対応できるよう、プレビューは動的にレイアウトする。

### Arrange画面の操作

1. ハブを開く。
2. Arrangeを選択する。
3. 保存済み初期レイアウト、または学習済み配置候補を読み込む。
4. 必要なウィンドウを選択する。
5. 配置先モニターを選択する。
6. 配置領域を指定する。
7. 必要なら別のウィンドウも同じ領域へ割り当てる。
8. 全体のプレビューを確認する。
9. Enterでまとめて適用する。

**ウィンドウを1つ設定するたびにハブを閉じない。**

すべての割り当てを完了してから一括適用できるようにする。

### ウィンドウ一覧

アプリ単位ではなく、ウィンドウ単位で扱う。

Chromeが2ウィンドウある場合は、それぞれ区別できるようにする。

ただし、独自のアプリ切り替え機能は作らない。

ハブ内で対象ウィンドウを選択することと、実際のデスクトップでアプリを切り替えることは別の機能として扱う。

### 重ねる配置

同じ領域に複数ウィンドウを割り当てられるようにする。

UI上では、例えば以下のように表現する。

- Zone 1：VS Code
- Zone 2：Chrome + Finder（2 Windows）
- Zone 3：Terminal

重なっていることが分かるように、小さなアイコンやウィンドウ数を表示する。

## 9.3 Edit画面

モニターごとの配置構造を編集する画面。

主に以下を操作する。

- 分割方向
- 分割数
- 分割比率
- 領域の追加
- 領域の削除
- 領域ごとのウィンドウ割り当て
- 重ねる領域の指定
- レイアウトの保存

モニター全体の配置図を大きめに表示し、選択中のモニター・領域・分割線を視覚的に強調する。

分割比率はキーボードとマウスの両方で調整可能とする。

Edit画面からArrange画面へ戻っても、未適用の編集内容は保持する。

# 10. キーボード操作設計

## 10.1 基本方針

**通常利用に必要なすべての操作を、キーボードのみで完結できることを目標とする。**

マウス・トラックパッド操作は補助的な操作方法とする。

OSによって異なる修飾キーを使わないよう、可能な限り共通のキー体系を使用する。

## 10.2 ハブの起動ショートカット

ハブを開くグローバルショートカットはユーザーが変更できるようにする。

初期候補：

`Ctrl + Shift + Space`

ただし、他アプリと競合する可能性があるため、自由に変更可能とする。

設定画面では、実際に押したキーの組み合わせを記録してショートカットを設定できるようにしたい。

設定は永続保存し、アプリ再起動後も維持する。

変更したキーが登録できない場合は、エラーを通知し、以前の有効な設定を保持する。

## 10.3 Home画面のキー操作

| キー | 動作 |
|---|---|
| `A` | Arrange |
| `Q` | Quick Move |
| `E` | Edit Layout |
| `S` | Saved Workspaces |
| `T` | テーマ設定 |
| `K` | ショートカット設定 |
| 矢印キー | メニュー内を移動 |
| Enter | 選択した機能を開く |
| Esc | ハブを閉じる |

TやKは設定画面へのショートカットとして扱ってもよい。

検索機能などを後で追加する場合は、文字入力との競合を考慮してキー割り当てを調整する。

## 10.4 Arrange画面のキー操作

| キー | 動作 |
|---|---|
| Tab | 次のウィンドウを選択 |
| Shift + Tab | 前のウィンドウを選択 |
| Ctrl + Tab | 次のモニターを選択 |
| Ctrl + Shift + Tab | 前のモニターを選択 |
| `1`〜`9` | 指定した領域へ割り当て |
| `R` | 比率編集 |
| `/` | 対象ウィンドウの検索・絞り込み |
| Enter | 一括配置を適用 |
| Esc | 前画面へ戻る |

複数ウィンドウを同一領域に割り当てられることを必須とする。

モニターや領域が選択されていることが視覚的に分かるようにする。

ウィンドウが多数ある場合でもTab連打だけに依存しないよう、検索機能を検討する。

## 10.5 Quick Move

直前まで操作していたウィンドウを対象とする。

基本配置は番号キーで即実行できるようにする。

初期割り当て案：

| キー | 動作 |
|---|---|
| `1` | 左半分 |
| `2` | 右半分 |
| `3` | 最大化 |
| `4` | 全画面表示 |
| `5` | 3分割レイアウトを選択 |
| `6` | 4分割レイアウトを選択 |

3分割・4分割の場合は、続けて配置領域を指定する。

Quick Moveでは単純な操作にEnterを要求しない。

複雑な配置や複数ウィンドウの一括変更ではEnterで確定する。

## 10.6 Escの統一

画面を戻る操作は`Esc`に統一する。

例えば、次のように動作する。

- Edit → Esc → Arrange
- Arrange → Esc → Home
- Home → Esc → ハブを閉じる

ただし、Homeから直接Editを開いた場合は、直前のHomeへ戻る。

つまり、画面名だけで固定的に遷移させるのではなく、画面履歴を保持して1つ前の画面へ戻る設計が望ましい。

ハブ内で編集した内容は、画面を戻っても保持する。

最終的にハブを閉じ、未適用の変更がある場合は、その変更を破棄する。

既に保存済みの初期レイアウトは変更しない。

## 10.7 ハブ内の操作ガイド

初めて使うユーザーが迷わないよう、各画面の下部に現在有効なキー操作を表示する。

例：

`TAB Window · CTRL+TAB Monitor · 1–9 Assign · ENTER Apply · ESC Back`

操作に慣れたら、ガイドをコンパクト表示または非表示にできるようにする。

設定画面にはショートカット一覧を設ける。

# 11. ハブのアニメーションと表示

## 11.1 アニメーション方針

近未来的ではあるが、派手すぎない演出を採用する。

- ハブの表示：140〜180ms程度
- 選択項目の移動：100〜140ms程度
- 画面の展開：150〜200ms程度
- 閉じる動作：短いフェード・スライド
- 選択中の表示：控えめなアクセントラインまたは背景色

過剰な発光・スプリングアニメーション・大きな拡大縮小は避ける。

アニメーションの無効化や軽減も設定可能にする。

## 11.2 ハブの表示中

ハブを開く直前に、アクティブだったウィンドウを記録する。

ハブ自体へフォーカスが移動しても、配置対象を誤認識しないようにする。

ハブを閉じたら、必要に応じて元のアプリへフォーカスを戻す。

通常時はメニューバー・システムトレイなどに常駐し、作業の邪魔にならないようにする。

# 12. 保存済みワークスペース

初期レイアウトとは別に、用途別のワークスペースを保存できるようにしたい。

例：

- Development
- Research
- General
- Custom

ワークスペースは、モニター構成と各アプリの配置をまとめて保存するものとする。

同じモニター構成でも、用途に応じて複数のワークスペースを使い分けられる。

ただし、特定のファイルやブラウザタブなど、アプリ内部の状態まで完全に復元する機能は初期実装の対象外とする。

まずは、起動中の対象ウィンドウの配置を復元できることを優先する。

# 14. 例外処理・制限事項

実際に利用できるソフトウェアにするため、以下を考慮する。

## 14.1 ウィンドウの最小サイズ

アプリ固有の最小サイズ制限により、指定領域に配置できない場合がある。

その場合は、適用できなかったウィンドウを明示する。

## 14.2 対象外ウィンドウ

以下は初期状態で自動配置の対象外にすることを検討する。

- システムダイアログ
- 一時的なポップアップ
- ウィンドウ管理できない特殊なアプリ
- 最小化中のウィンドウ
- OS固有の管理ウィンドウ

ユーザーによる除外アプリ設定も検討する。

## 14.3 最大化と全画面表示

最大化とネイティブフルスクリーンは区別する。

macOSではフルスクリーン時にSpaceが変化することがあり、Windowsではアプリによってフルスクリーンの実装が異なる。

すべてのアプリで真のフルスクリーン表示ができるとは限らない。

対応できない場合は適切に通知する。

## 14.4 モニターの接続変更

モニターが外された場合、存在しない画面座標へウィンドウを配置しない。

現在利用可能なモニターを再取得し、必要に応じて配置を再計算する。

ただし、モニター接続のたびに自動的にすべてのウィンドウを動かさない。

## 14.5 macOSの権限

他アプリのウィンドウを操作するためにアクセシビリティ権限が必要になる。

初回起動時に、ユーザーが許可できる案内画面を設ける。

## 14.6 Windows固有の制約

管理者権限の違いや、特殊なアプリのウィンドウ操作制限を考慮する。

また、画面倍率、複数モニター座標、仮想デスクトップなどに関する挙動も検証する。

Undo / Redoは優先度を下げる。

ユーザーは、配置ミスが発生しても手動で再配置すればよいと考えている。

そのため、初期実装ではUndo / Redoを必須としない。

代わりに、以下を重視する。

- 配置前のプレビュー

- 編集内容の明確な表示
- Escによる画面遷移
- 未適用変更の破棄
- 保存済み初期レイアウトの保護

後からUndoを追加できる余地は残してもよいが、初期の開発優先度は低い。

# 24. 最終的に目指すユーザー体験

ユーザーはPCで複数のアプリを開いて作業している。

ハブのショートカットを押すと、現在のモニターの上部中央に、アースカラーを基調としたコンパクトなハブが滑らかに表示される。

ハブは現在のモニター構成を認識しており、以前設定した初期レイアウトを読み込んでいる。

ユーザーはキーボードでArrangeを開き、全モニターの配置を確認する。

必要であればTabで対象ウィンドウを切り替え、配置先を指定する。

1つの領域に複数ウィンドウを重ねることもできる。

分割比率が気に入らなければ、Editで矢印キーを使って調整する。必要に応じてカーソルで微調整してもよい。

すべての設定が完了したらEnterを押す。

指定された複数のウィンドウが、複数モニターへまとめて配置される。

ハブは閉じ、ユーザーはそのまま作業を再開できる。

次回同じモニター構成を使うときには、以前設定したレイアウトを呼び出せる。

また、普段の配置傾向が蓄積され、将来的にはユーザーに適した別の配置候補も提示される。

**目指すのは、マウスに頼らず、少ない操作で、複雑なマルチモニター環境を整理できるアプリケーションである。**

見た目は落ち着いたアースカラーの近未来的デザインとし、OSに依存しない統一された操作体験を提供する。

この設計思想を維持した上で、実装を進めてほしい。
